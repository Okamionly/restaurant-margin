## Bug détecté

**Fichier** : `client/src/pages/MenuCalendar.tsx`  
**Fonction** : `handleDrop` (drag & drop calendrier menu)  
**Lignes** : ~444-466 (avant fix)

### Problème
Race condition de données : lors du déplacement d'une entrée par drag & drop, le code exécutait d'abord le `DELETE` de l'entrée source, puis le `POST` pour créer l'entrée à la nouvelle date. Si le `POST` échouait (réseau, 500 serveur), l'entrée était définitivement supprimée en base mais toujours visible en UI → état incohérent. Après rechargement, l'entrée disparaissait silencieusement.

Bonus : `setDragEntry(null)` était hors du bloc try/catch, non garanti en cas d'exception précoce.

### Avant
```typescript
try {
  await fetch(`/api/menu-calendar/${dragEntry.id}`, { method: 'DELETE', ... });
  // Si le POST ci-dessous échoue → entrée perdue en base, UI incohérente
  const res = await fetch('/api/menu-calendar', { method: 'POST', ... });
  ...
} catch {
  showToast('Erreur lors du déplacement', 'error');
}
setDragEntry(null); // hors du try/catch
```

### Après
```typescript
const snapshot = entries; // sauvegarde pour rollback
try {
  // POST en premier : si échec, l'entrée source est intacte en base
  const res = await fetch('/api/menu-calendar', { method: 'POST', ... });
  if (!res.ok) throw new Error('Erreur');
  const created = await res.json();
  await fetch(`/api/menu-calendar/${dragEntry.id}`, { method: 'DELETE', ... });
  setEntries(prev => [...prev.filter(e => e.id !== dragEntry.id), ...created]);
  showToast(`... déplacé`, 'success');
} catch {
  setEntries(snapshot); // rollback UI si erreur
  showToast('Erreur lors du déplacement', 'error');
} finally {
  setDragEntry(null); // garanti dans tous les cas
}
```

## Impact
- Données calendrier menu protégées contre la perte silencieuse lors d'erreurs réseau
- Rollback UI cohérent avec l'état base de données en cas d'échec
- `setDragEntry(null)` désormais garanti via `finally`
