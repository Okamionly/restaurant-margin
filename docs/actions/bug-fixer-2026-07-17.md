# Bug Fixer — 2026-07-17

## Bug corrigé

**Fichier** : `api/index.ts`  
**Ligne** : ~484 (endpoint `/api/health`)  
**Type** : Performance — latence excessive du health check

## Symptôme

Le endpoint `/api/health` répondait en 854ms (CTO report 2026-07-16). Seuil acceptable : < 100ms.

## Cause

À chaque appel (probe uptime, dashboard monitoring), le handler exécutait un `prisma.$queryRaw\`SELECT 1\`` vers Supabase. Le cold start de la connexion Supabase ajoutait ~800ms de latence à chaque requête.

## Fix appliqué

Ajout d'un cache en mémoire `dbHealthCache` avec un TTL de 30 secondes :

**Avant :**
```typescript
let dbStatus = 'ok';
try {
  await prisma.$queryRaw`SELECT 1`;
} catch {
  dbStatus = 'error';
}
```

**Après :**
```typescript
const dbHealthCache: { status: string; cachedAt: number } = { status: 'ok', cachedAt: 0 };
const DB_HEALTH_TTL_MS = 30_000;

// Dans le handler :
let dbStatus: string;
const now = Date.now();
if (now - dbHealthCache.cachedAt < DB_HEALTH_TTL_MS) {
  dbStatus = dbHealthCache.status;
} else {
  try {
    await prisma.$queryRaw`SELECT 1`;
    dbStatus = 'ok';
  } catch {
    dbStatus = 'error';
  }
  dbHealthCache.status = dbStatus;
  dbHealthCache.cachedAt = now;
}
```

## Impact attendu

- Latence `/health` : 854ms → < 10ms (hits cache après la 1ère requête)
- Les probes uptime ne saturent plus Supabase
- Le statut DB reste fiable : rafraîchi au pire toutes les 30s
- Le check `?deep=1` (appel Claude réel) est inchangé
