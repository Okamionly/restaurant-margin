## Bug sélectionné

**Titre** : Cold start API élevée (~841ms) due à connexion Prisma lazy  
**Priorité** : Recommandation CTO explicite (#3 dans "Dette technique")  
**Impact** : 1ère requête post-cold-start ~800ms de latence supplémentaire

---

## Analyse

La serverless function `api/index.ts` utilise `prisma` depuis `api-lib/prisma.ts` (singleton correctement configuré).  
Cependant, Prisma ne se connecte à la base que lors du **premier `$queryRaw` ou `prisma.*` appelé**.  
Sur Vercel, chaque cold start recharge le module → connexion TCP/TLS/auth PostgreSQL est reétablie à la 1ère vraie requête, ajoutant ~800ms.

---

## Fix

**Fichier** : `api/index.ts`  
**Ligne** : ~38 (après `const anthropic = new Anthropic(...)`)

**Avant** :
```ts
const anthropic = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY || '' });

const JWT_SECRET = process.env.JWT_SECRET;
```

**Après** :
```ts
const anthropic = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY || '' });

// Eager DB warm-up: pre-connect on cold start so first real request doesn't pay
// the TCP + TLS + auth handshake cost (was causing ~800ms cold-start latency).
prisma.$connect().catch((err) => console.error('[DB WARMUP]', err));

const JWT_SECRET = process.env.JWT_SECRET;
```

**Raison** : `prisma.$connect()` est fire-and-forget (non-bloquant). Il démarre la connexion TCP/TLS/auth en parallèle du chargement du reste du module. Quand la 1ère requête arrive, la connexion est déjà (ou presque) établie → latence réduite.

---

## Résultat attendu

- Cold start : 841ms → objectif < 200ms sur les requêtes suivant la connexion
- Aucun impact sur les requêtes normales (prisma est déjà connecté si invocation chaude)
- `[DB WARMUP]` dans les logs uniquement si erreur de connexion
