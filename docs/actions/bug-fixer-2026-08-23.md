## Fix appliqué

**Fichier** : `api/index.ts`  
**Lignes modifiées** : ~39–60 (warm-up) + ~496–498 (suppression dupliquée)

### Problème

`dbHealthCache` était déclaré à la ligne ~496, après le warm-up DB à la ligne ~41.  
Résultat : même avec `prisma.$connect()` au démarrage, le premier appel `/api/health`
trouvait le cache expiré (`cachedAt: 0`) et exécutait un `SELECT 1` Supabase complet
→ **418 ms de latence sur la première probe**.

### Fix

1. Déplacé `dbHealthCache` et `DB_HEALTH_TTL_MS` **avant** `prisma.$connect()`.
2. Étendu le warm-up pour enchaîner un `SELECT 1` après `$connect()` et **pré-remplir le cache** :
   ```ts
   prisma.$connect()
     .then(() => prisma.$queryRaw`SELECT 1`)
     .then(() => {
       dbHealthCache.status = 'ok';
       dbHealthCache.cachedAt = Date.now();
     })
     .catch(...)
   ```
3. Supprimé les déclarations dupliquées dans la section health check.

### Avant / Après

| Situation | Latence première probe `/api/health` |
|-----------|--------------------------------------|
| Avant fix | ~418 ms (SELECT 1 Supabase en direct) |
| Après fix | ~1 ms (cache pré-rempli au démarrage) |
