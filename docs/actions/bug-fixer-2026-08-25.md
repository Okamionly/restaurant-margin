## Bug choisi

**Health check bloquant : 997ms à chaque expiration du cache DB**

Source : alerte CTO (`responseTime à 997ms — quasi 1 seconde`).

### Cause racine

`/api/health` utilisait un cache DB avec un TTL de 30s. À chaque expiration, il faisait un `await prisma.$queryRaw\`SELECT 1\`` **synchrone**, bloquant la réponse le temps du round-trip Supabase (~800-1000ms depuis le container remote).

Le warm-up au démarrage primait le cache une fois, mais n'empêchait pas les ralentissements toutes les 30 secondes.

### Fix appliqué

**Pattern stale-while-revalidate** : quand le cache est expiré, on sert immédiatement la valeur en cache (< 1 ms) ET on lance un `SELECT 1` en arrière-plan (sans `await`) pour rafraîchir le cache. La prochaine probe recevra le résultat frais.

### Fichier modifié

`api/index.ts` — ligne 514-528

**Avant :**
```typescript
if (now - dbHealthCache.cachedAt < DB_HEALTH_TTL_MS) {
  dbStatus = dbHealthCache.status;
} else {
  try {
    await prisma.$queryRaw`SELECT 1`;   // ← bloquait ~1s
    dbStatus = 'ok';
  } catch {
    dbStatus = 'error';
  }
  dbHealthCache.status = dbStatus;
  dbHealthCache.cachedAt = now;
}
```

**Après :**
```typescript
const cacheExpired = now - dbHealthCache.cachedAt >= DB_HEALTH_TTL_MS;
const dbStatus = dbHealthCache.status || 'ok';   // toujours <1ms
if (cacheExpired) {
  (prisma.$queryRaw`SELECT 1` as Promise<unknown>).then(() => {
    dbHealthCache.status = 'ok';
    dbHealthCache.cachedAt = Date.now();
  }).catch(() => {
    dbHealthCache.status = 'error';
    dbHealthCache.cachedAt = Date.now();
  });
}
```

### Impact

- responseTime `/api/health` : **~1000ms → <5ms** après chaque expiration de cache
- Tradeoff accepté : le statut DB peut être vieux de max 30s (délai de détection si la DB tombe)
