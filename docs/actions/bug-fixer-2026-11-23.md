## Bug choisi

**Fichier** : `api-lib/routes/auth.ts`, ligne 438  
**Type** : hash bcrypt invalide stocké lors de la suppression admin d'un compte

### Avant
```typescript
data: { email: `deleted_${targetId}_${Date.now()}@deleted.local`, passwordHash: 'DELETED', role: 'deleted' },
```

### Après
```typescript
const scrambledHash = await bcrypt.hash(crypto.randomBytes(32).toString('hex'), 12);
await prisma.user.update({
  where: { id: targetId },
  data: { email: `deleted_${targetId}_${Date.now()}@deleted.local`, passwordHash: scrambledHash, role: 'deleted' },
});
```

### Raison

La valeur littérale `'DELETED'` n'est pas un hash bcrypt valide (ne commence pas par `$2a$` ou `$2b$`).
Si `bcrypt.compare()` est appelé avec ce hash (ex. : tentative de connexion sur l'email renommé du compte supprimé),
la librairie bcryptjs lève une exception — capturée par le `catch` du handler login — qui répond **500** au lieu de **401**.

La QA du 2026-11-22 avait détecté un 500 sur la route login (régression).
Le test live depuis ce runner confirme que l'endpoint répond maintenant 401 sur credentials invalides.
Le bug racine est corrigé pour éviter toute récurrence si un compte supprimé par admin est un jour retrouvé lors d'un login.

Alignement avec la voie RGPD (ligne 351) qui génère déjà un hash aléatoire pour l'anonymisation.
