# SEO Daily Push — 2026-09-19 (Samedi)

## Résultat du jour : cause du LCP identifiée et mesurée — correctif tenté, **mesuré, puis REVERTÉ**

Rotation samedi = Core Web Vitals. L'audit n'a pas porté sur le poids des assets ni sur les
en-têtes de cache (déjà optimaux, vérifiés le 12/09) mais sur une **mesure LCP réelle** en
émulation mobile (412×915, CPU ×4, réseau ~1,6 Mb/s).

**Le livrable du jour est un diagnostic, pas un patch** : le LCP de RestauMargin est borné par
le **CPU**, pas par le réseau. Le correctif réseau construit ce matin a été mesuré en production,
s'est révélé coûteux, et a été annulé le jour même.

### 1. Mesures de départ (prod, mobile throttlé)

| Page | LCP | FCP | CLS | Long tasks |
|---|---|---|---|---|
| `/` | **3748 ms** (élément TEXTE, H1) | 1676 ms | 0 | 56 tâches / **7532 ms** |
| `/blog/calcul-marge-restaurant` | **2688 ms** (élément TEXTE, P) | 1668 ms | 0 | 94 tâches / **8372 ms** |

TTFB : 102 ms (`/`), 295 ms (blog), 356 ms (`/pricing`) — aucun problème serveur.
CLS = 0 sur les deux pages : rien à faire de ce côté.

Le LCP est un élément **texte** (pas une image) et arrive ~2 s après le FCP. Les pistes
habituelles étaient déjà traitées : Crisp et Sentry différés (interaction ou idle 8 s),
preconnect Fontshare en place depuis le 06/09, fonds WebGL `lazy` et respectant
`prefers-reduced-motion`.

### 2. Cause identifiée dans le waterfall (fait établi, toujours vrai)

Sur `/`, `index.js` finit à ~1356 ms mais `Landing-*.js` (67 Ko) n'est **découvert qu'à
1682 ms** ; même schéma sur l'article (`BlogCalcMarge-*.js` à 1747 ms). Ces chunks viennent d'un
`import()` dynamique : le navigateur ne peut pas les anticiper. Vite n'émet des
`<link rel="modulepreload">` que pour les imports **statiques** de l'entry (`vendor-react`,
`vendor-icons`) — confirmé dans le HTML servi, qui n'en contenait que 2.

### 3. Correctif tenté : préchargement du chunk de route

`prerender.cjs` dérivait la table route → chunk depuis `App.tsx` et `dist/assets/`, et injectait
un `<link rel="modulepreload" data-route-chunk>` par page (132 pages). Gardes : motif de fichier
ancré (`^Nom-hash.js$`), refus de tout path déclaré avec deux composants différents
(`path="/"` existe deux fois : Dashboard authentifié vs PublicHome visiteur), aucune injection
en cas de doute, nettoyage du marqueur pour rester idempotent.

Déployé (`44cff3e`), vérifié en prod : les 4 pages testées servaient leur hint, chaque asset
répondait 200, et **le chunk démarrait à ~270 ms au lieu de 1610-1786 ms**. Aucune erreur
console, contenu et titles intacts.

### 4. Ce que la mesure a dit — et pourquoi j'ai reverté

A/B en **conditions de production** : même serveur, même CDN, même réseau ; le bras témoin reçoit
le HTML réel de prod avec la seule ligne du hint retirée à la volée (interception vérifiée :
1 occurrence → 0, DOM confirmé vide). Ordre des bras alterné pour neutraliser la dérive machine.

| Page | Δ LCP | Δ FCP | Δ chunkStart |
|---|---|---|---|
| `/blog/calcul-marge-restaurant` (6 runs) | **+878 ms** | +296 ms | −1490 ms |
| `/` (8 runs) | −114 ms (bruit) | +346 ms | −1336 ms |

- **Δ LCP incohérent** entre les deux pages (+878 vs −114), distributions entièrement
  chevauchantes → **aucun gain démontrable**.
- **Δ FCP cohérent et négatif** sur les deux (~+300 ms) → coût réel et reproductible.

Le hint prend de la bande passante au CSS et à l'entry pendant la fenêtre critique, et Vite
injecte de toute façon ses propres `modulepreload` au moment du `import()` dynamique (vérifié
dans le DOM : 6 hints ajoutés dynamiquement). Le gain réseau est réel mais **ne se convertit
pas**, parce que le goulot est ailleurs.

**Revert `c9bb089` déployé et vérifié** : 0 hint en prod sur `/`, l'article et `/pricing`,
titles intacts, deploy `success` sur les deux projets. `git diff 3fb0bba..HEAD` sur le code est
**vide** — le dépôt est exactement dans son état d'avant le run.

### 5. Conclusion technique (le vrai livrable)

**Le LCP des pages publiques est CPU-bound, pas réseau-bound.** 56 à 94 long tasks pour 7,5 à
8,4 s de blocage cumulé du thread principal (mobile, CPU ×4). Tant que ce travail JS n'est pas
réduit, avancer une ressource de 1,4 s ne déplace pas le LCP. **Le prochain levier technique est
la réduction du travail JS au démarrage, pas les hints de ressources** — cette piste est
désormais fermée, mesurée, à ne pas rouvrir sans chiffre contraire.
