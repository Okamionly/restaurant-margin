## Mesure : A/B des fonds WebGL sur /blog/calcul-marge-restaurant (prod)

Conditions : Playwright headless, mobile 412x915, CPU x4, réseau ~1,6 Mb/s + 150 ms, cache
désactivé, bras alternés, 6 runs par bras. Bras B = chunks `ShaderBackground`,
`MintMistBackground`, `PaperFoldBackground` bloqués (`route.abort`), 0 canvas vérifié.
Un run B invalide exclu (blocage non appliqué : 0 chunk bloqué, 2 canvas) — il est dans les
données brutes, et la médiane ne change pas de sens avec ou sans lui.

| Bras | LCP médian | FCP médian | Long tasks médian |
|---|---|---|---|
| Avec shaders | 3396 ms | 1852 ms | 8609 ms (≈85 tâches) |
| Sans shaders | 3608 ms | 2108 ms | 1980 ms (≈10 tâches) |

- **LCP : aucun gain** (écart dans le bruit, distributions chevauchantes). L'élément LCP reste
  un `<p>` de l'article dans les deux bras.
- **Long tasks : −6,6 s**, mais c'est un **artefact de mesure** : le Chromium headless rend le
  WebGL via **SwiftShader** (renderer vérifié : `ANGLE (… SwiftShader Device (Subzero) …)`),
  donc chaque frame de shader est exécutée par le CPU, puis multipliée par le throttling x4.
  Sur un vrai téléphone, le fragment shader tourne sur le GPU.

## Conséquence pour les mesures passées

Le chiffre « 7,5–8,4 s de long tasks » du 2026-09-19 (home + article) était gonflé par le
même artefact : ~6,6 s sur ~8,6 s viennent du rendu logiciel des shaders. Le « CPU-bound »
réel au chargement est donc de l'ordre de **~2 s**, pas 8 s. La conclusion d'alors (les hints
ne déplacent pas le LCP) tient, mais sa justification chiffrée doit être relue avec ce biais.

## Le levier qui reste

FCP ~1,9 s → LCP ~3,4 s : l'écart correspond au rendu du corps de l'article par le JS
(le prerender n'injecte que les métadonnées, pas le contenu). Le seul levier LCP crédible est
de **prérendre le corps HTML des articles** — chantier à part entière (hydratation, 132 pages),
pas un correctif de samedi. À proposer au fondateur.
